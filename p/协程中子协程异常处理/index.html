协程中子协程异常处理

2024-12-17
阅读时长: 5 分钟

本文通过案例来熟悉子协程到父协程之间的异常是如何处理的。

private fun demo1() {
    val handler = CoroutineExceptionHandler { coroutineContext, throwable ->
        Log.d(TAG, "onCreate: CoroutineExceptionHandler:${throwable.message}")
    }
    GlobalScope.launch(handler) {
        Log.d(TAG, "onCreate: parentJob start")
        withContext(Dispatchers.IO) {
            throw RuntimeException("runtime exception")
            delay(1000)
            Log.d(TAG, "onCreate: withContext end")
        }
        Log.d(TAG, "onCreate: parentJob end")
    }
}

先上日志：

1
2

com.example.coroutinescopedemo       D  onCreate: parentJob start
com.example.coroutinescopedemo       D  onCreate: CoroutineExceptionHandler:withContext runtime exception

结论：异常能被launch指定的handler所捕捉。
分析： launch启动的协程用到的coroutineScope是一个StandaloneCoroutine，withContext启动的协程对应的coroutineScope是一个DispatchedCoroutine（因为父context和子context的dispatcher不一样，所以创建的是DispatchedCoroutine）。 在withContext中发生异常的时候，首先会回调到DispatchedCoroutine的resumeWith，最终会走到finalizeFinishingState方法，该方法里面会判断是否存在异常，如果有异常会调用cancelParent方法：

可以看到如果 isScopedCoroutine 为 true，cancelParent 会直接返回 true。这里的 true 不是表示继续调用 parent.childCancelled 交给父 Job，而是表示当前 scoped coroutine 已经“处理”了这个异常：它不会触发自己的 handleJobException，也不会走自己 context 里的 CoroutineExceptionHandler，而是把异常作为挂起函数的失败结果抛回调用它的挂起点。

在这个例子里，withContext(Dispatchers.IO) 对应的是 DispatchedCoroutine，它属于 scoped coroutine，所以异常会先抛回外层 launch 中调用 withContext 的位置。外层 launch 没有用 try-catch 接住这个异常，于是 launch 自己异常完成。GlobalScope.launch(handler) 创建的是根 StandaloneCoroutine，没有普通父 Job 再接手，最终会走到自己的 handleJobException，再从 context 里找到前面传入的 CoroutineExceptionHandler，所以日志里能看到 CoroutineExceptionHandler:runtime exception。

总结：这个异常不是被 withContext 自己的 handler 处理，也不是 withContext 继续通过 parent.childCancelled 交给父 Job。真实流程是：withContext 内部抛异常 → scoped coroutine 不走自己的 handleJobException → 异常抛回外层 launch 的挂起点 → 外层 launch 因异常失败 → 根 StandaloneCoroutine 走 handleJobException → GlobalScope.launch(handler) 上的 CoroutineExceptionHandler 兜底处理。

案例二：子协程异常，子协程try-catch捕捉

上面代码如果把withContext中的异常通过try-catch住，父job就收不到该异常了： 子协程把异常catch住后，父协程的handler捕捉不到异常，并且父协程的invokeOnCompletion收不到异常，父协程之后的代码也能正常执行。因为在子协程对应的SuspendLambda中的invokeSuspend方法给try-catch住，不会把异常往上抛。

案例三：子协程的handler无法捕捉

子协程给context传递coroutineExceptionHandler：

这里容易误解：handler 传到 withContext 的 context 里，并不代表它一定会回调。withContext 创建的是 DispatchedCoroutine，它属于 scoped coroutine，isScopedCoroutine=true 时，cancelParent 会直接返回 true，自己的 handleJobException 不会触发，所以 context 里的 CoroutineExceptionHandler 也没有机会执行。

这个异常会作为 withContext 这个挂起点的失败结果抛回外层 launch。外层没有 try-catch，所以父协程异常完成，invokeOnCompletion 能收到原始异常，后面的 onCreate: parentJob end 也不会执行。

结论：案例三的子 handler 没执行，原因在 withContext 的异常传播路径：先回到调用它的父协程挂起点，再由父协程处理。想在这个位置消费异常，用 try-catch 包住 withContext；想让子协程自己兜底，通常要把它放在 supervisorScope / SupervisorJob 这类不会向上取消父级的关系里，后面的案例会继续看。

案例四：子协程抛CancellationException，父协程无法捕捉

当子协程抛的是CancellationException，父协程捕捉不到该异常：

这里 handler 没有回调，程序也没有崩溃。原因是 CancellationException 在协程里不是普通失败，而是取消信号。

这个例子里的 withContext(Dispatchers.IO) 对应的是 DispatchedCoroutine，它属于 scoped coroutine。内部抛出 CancellationException 后，会先进入 withContext 自己的完成流程；因为 isScopedCoroutine=true，cancelParent 直接返回 true，不会触发 withContext 自己的 handleJobException，也不会走 withContext context 里的 CoroutineExceptionHandler。接着这个 CancellationException 会作为 withContext 的失败结果，抛回外层 launch 调用 withContext 的挂起点。

外层 launch 收到的是 CancellationException，所以它会按取消完成处理，而不是按普通异常失败处理。后续在 JobSupport.cancelParent 中会判断 cause is CancellationException，并直接返回 true，因此不会继续走 StandaloneCoroutine.handleJobException，handler 也就不会回调。

日志里能看到 job exception:cancel exception，是因为 invokeOnCompletion 会收到这个取消原因；看不到 CoroutineExceptionHandler 日志，是因为 CancellationException 不会按未捕获异常兜底处理。

总结：CancellationException 的意义是告诉协程“这次是取消，不是业务失败”。它可以让协程停止，并把取消原因传给 invokeOnCompletion，但不会进入 CoroutineExceptionHandler。如果业务代码 catch 住了它，通常要重新抛出，否则可能破坏协程取消传播。

private fun demo2() {
    val handler = CoroutineExceptionHandler { coroutineContext, throwable ->
        Log.d(TAG, "handler:${throwable.message}")
    }
    val job = Job()
    val coroutineScope = CoroutineScope(job + handler)
    val job1 = coroutineScope.launch {
        delay(100)
        Log.d(TAG, "job1 end")
        throw RuntimeException("runtime exception")
    }
    job1.invokeOnCompletion {
        Log.d(TAG, "job1 invokeOnCompletion:${it?.message}")
    }
    val job2 = coroutineScope.launch {
        delay(200)
        Log.d(TAG, "job2 end")
    }
    job2.invokeOnCompletion {
        Log.d(TAG, "job2 invokeOnCompletion:${it?.message}")
    }
    val job3 = coroutineScope.launch {
        delay(300)
        Log.d(TAG, "job3 end")
    }
    job3.invokeOnCompletion {
        Log.d(TAG, "job3 invokeOnCompletion:${it?.javaClass?.simpleName}")
        Log.d(TAG, "job3 invokeOnCompletion:${it?.message}")
    }
}

             |        |
             |        v
             |      job2: StandaloneCoroutine
             |        state -> NodeList(InvokeOnCompletion, ChildContinuation)
             |
             +-- ChildHandleNode(job=parentJob, childJob=job3) <--- job3.parentHandle
                      |
                      v
                    job3: StandaloneCoroutine
                      state -> NodeList(InvokeOnCompletion, ChildContinuation)

每个子协程启动时，都会向父 JobImpl 注册一个 ChildHandleNode。这个节点的 job 指向父 Job，childJob 指向当前子 Job；子 Job 自己的 parentHandle 又指回这个 ChildHandleNode。所以父 Job 的 state 最后会变成一个 NodeList，里面挂着三个子协程对应的 ChildHandleNode。

子 Job 自己也有一套 state。这里每个 Job 都注册了 invokeOnCompletion，所以会有 InvokeOnCompletion 节点；执行到 delay 挂起时，还会创建 CancellableContinuationImpl，并通过 ChildContinuation 注册到当前子 Job 上。这样父 Job 取消子 Job 时，挂起点也能收到取消信号。

当 job1 抛出 RuntimeException 后，它会先进入自己的完成流程，把 state 置成 Finishing，并记录原始异常。接着 job1.cancelParent 会通过 parentHandle.childCancelled 找到父 JobImpl，父 Job 收到子协程异常后，也进入取消流程。

父 Job 取消时会遍历自己 NodeList 里的 ChildHandleNode，依次调用每个 childJob.parentCancelled。所以 job2、job3 会被父 Job 取消，它们拿到的是 JobCancellationException("Parent job is Cancelling")，这个异常再通过各自的 ChildContinuation 分发到挂起点，最后触发 invokeOnCompletion。

job1 自己已经是异常完成，后面不会用 JobCancellationException 覆盖原始异常。它在完成流程里调用 cancelParent(RuntimeException)，这个调用会通过父 JobImpl 触发其它子协程取消；由于父 JobImpl 不负责兜底处理异常，childCancelled 最终返回 false，所以 job1.cancelParent 也返回 false。接着 job1 走到自己的 handleJobException，从 context 里找到 CoroutineExceptionHandler，日志里才会打印 handler:runtime exception。最后 job1 自己的 invokeOnCompletion 收到原始的 RuntimeException。

所以上面的日志顺序是：job2、job3 先收到父 Job 取消带来的 JobCancellationException，然后 CoroutineExceptionHandler 收到 job1 的原始异常，最后 job1.invokeOnCompletion 收到同一个原始异常。

private fun demo3() {
    val handler = CoroutineExceptionHandler { coroutineContext, throwable ->
        Log.d(TAG, "handler:${throwable.message}")
    }
    val coroutineScope = CoroutineScope(SupervisorJob() + handler)
    val job1 = coroutineScope.launch {
        delay(100)
        Log.d(TAG, "job1 end")
        throw RuntimeException("runtime exception")
    }
    job1.invokeOnCompletion {
        Log.d(TAG, "job1 invokeOnCompletion:${it?.message}")
    }
    val job2 = coroutineScope.launch {
        delay(200)
        Log.d(TAG, "job2 end")
    }
    job2.invokeOnCompletion {
        Log.d(TAG, "job2 invokeOnCompletion:${it?.message}")
    }
    val job3 = coroutineScope.launch {
        delay(300)
        Log.d(TAG, "job3 end")
    }
    job3.invokeOnCompletion {
        Log.d(TAG, "job3 invokeOnCompletion:${it?.javaClass?.simpleName}")
        Log.d(TAG, "job3 invokeOnCompletion:${it?.message}")
    }
}

这里和案例五的差异只在父 Job：Job() 换成了 SupervisorJob()。父子关系还是通过 ChildHandleNode 建立，父 Job 的 state 里也仍然挂着 job1、job2、job3 对应的子节点。

区别发生在 job1 抛异常后。job1.cancelParent(RuntimeException) 会通过 parentHandle.childCancelled 调到父 Job，但这次父 Job 是 SupervisorJobImpl，它的 childCancelled 直接返回 false。所以父 Job 不会因为 job1 的异常进入取消流程，也不会遍历自己的 NodeList 去取消 job2、job3，后两个协程可以继续执行完。

这个 false 还有另一层含义：父 SupervisorJob 没有兜底处理 job1 的异常。于是异常回到 job1 自己的完成流程，job1 会继续走 handleJobException，从 coroutine context 里找到 CoroutineExceptionHandler。这里的 handler 是创建 CoroutineScope(SupervisorJob() + handler) 时放进 scope context 的，子 launch 会继承它，所以最后日志里能看到 handler:runtime exception。

结论：SupervisorJob 只改变“子协程失败是否取消父级和兄弟协程”这条链路，不会吞掉异常。失败的 job1 还是要自己完成异常处理；只是 job2、job3 不会被连带取消。

案例七：try-catch在非异常协程位置，无法捕捉

结果：try-catch竟然捕获不住，程序直接抛异常了

private fun demo7() {
    val scope = CoroutineScope(Dispatchers.Main + Job())
    scope.launch(CoroutineName("job1")) {
        Log.d(TAG, "scope1:$this")
        try {
            thirdApi(this)
        } catch (e: Exception) {
            Log.d(TAG, "demo7: e:${e.message}")
        }
    }
}
private fun thirdApi(coroutineScope: CoroutineScope) {
    coroutineScope.launch(CoroutineName("job2")) {
        Log.d(TAG, "thirdApi: start")
        delay(100)
        Log.d(TAG, "thirdApi: end")
        throw NullPointerException("null pointer exception")
    }
}

这里的 try-catch 包住的是 thirdApi(this) 这次普通函数调用。thirdApi 内部只是同步执行了一次 launch，创建出 job2 后就返回了，所以 catch 能兜住的范围只有“启动 job2”这个动作。

从字节码看，try-catch 确实只套在调用 thirdApi 的位置。job2 里面真正抛异常的位置在 delay(100) 之后，那时 job1.invokeSuspend 里这段 try-catch 已经执行完了。

100ms 后：
job2 抛 NullPointerException
  -> job2.cancelParent
  -> job1.childCancelled
  -> job1 进入 Cancelling / Finishing，记录 job2 的异常

job2 继续完成自己的收尾
  -> job2.notifyCompletion
  -> ChildCompletion.invoke
  -> job1.continueCompleting
  -> job1.finalizeFinishingState
  -> job1.handleJobException
  -> 没有 handler 就崩溃

源码里还能看到一个细节：job1 启动 job2 后，会在 job2 的 state 里挂一个 ChildCompletion。这个节点不是给外层 try-catch 用的，它是父子 Job 完成流程用的。job2.cancelParent 会先把异常传给 job1，让 job1 记录异常并进入取消流程；等 job2 自己完成收尾时，notifyCompletion 会触发 ChildCompletion.invoke，再回到 job1.continueCompleting，让 job1 继续完成自己的异常处理。

所以这个例子里，try-catch 写在 thirdApi(this) 外面没有用。要么把 try-catch 写进 job2 的协程体里，要么让 thirdApi 暴露一个会重新抛异常的挂起函数；单纯包住 launch 调用，接不住子协程后面异步抛出来的异常。

案例八：异常job的父job处增加CoroutineExceptionHandler捕捉异常

这个例子和案例七的路径一样。异常还是从 job2 抛出，先通过 job2.cancelParent 传给父协程 job1；job1 进入取消流程后记录这个异常，等 job2 自己收尾完成，ChildCompletion.invoke 再把流程带回 job1.continueCompleting，最后由 job1 走到 handleJobException。

区别在于，这次 CoroutineExceptionHandler 放在了 job1 的 context 里。job1.handleJobException 查自己的 context 时能找到 handler，所以异常会在这里被兜底处理，日志里会打印 handler 的内容，程序不会崩溃。

结论：这个场景里最终处理异常的是父协程 job1，所以 handler 要放在 job1 这一层才有效。外层 try-catch 接不住 job2 后面异步抛出的异常，但 job1 context 里的 CoroutineExceptionHandler 可以兜底。

案例九：handler给到异常协程，handler捕获不到异常

分析：结合案例七的分析，最终是在job1中处理异常，而此处设置的handler是设置到job2处了，所以程序崩溃了。

案例十：增加coroutineScope，异常协程的父协程增加try-catch捕捉异常

结果：程序不会崩溃，异常被try catch捕获住，而不是被exceptionHandler捕获住。

前面分析过当子协程发生异常后，会把异常分发给到父job，在父job中需要等子job都处理完异常了，才会往下走，该处逻辑主要体现在子job中添加了一个ChildCompletion节点到state中，在invoke中会执行到parent.continueCompletion方法： 此处的parent实际是coroutineScope作用域的job，它是ScopeCoroutine，看下它的continueCompleting实现： 最终会把结果回调给到了传递进来的continuation，也就是最外层launch启动的时候的SuspendLambda，最终会调用它的invokeSuspend方法： 所以最终被try-catch捕捉到异常。

案例十一：增加supervisorScope作为异常协程的作用域，异常能被异常协程的handler所捕获

结果：程序被内层launch指定的exceptionHandler捕捉了 supervisorScope用到的job是SupervisorCoroutine，它重写了childCancel方法，并返回false，所以当子job发生异常的时候，不会抛给父job，并执行自己的handleJobException方法，所以被自己的handler捕获到。

总结

父子协程关系：父子协程之间通过job建立起关系，在子协程的job初始化的时候，会通过childHandleNode绑定到父子关系，其中子job指向childHandleNode的childJob，父job指向childHandleNode的job上，最后子job通过parentHandle持有该childHandleNode。父协程中如何包含了多个子协程，此时父job的state会是一个NodeList，也就是链表结构的对象，然后NodeList的next节点持有了第一个子协程的childHandleNode，第一个子协程的childHandleNode的next节点持有了第二个子协程的childHandleNode，依次类推。
异常处理：当某个子协程发生异常后，会将自己的state给置为Finishing状态，并且给Finishing状态添加异常信息，接着将异常给到父协程，如果此时父协程不处理异常，则交给自己的context中的CoroutineExceptionHandler处理，如果context中找不到CoroutineExceptionHandler，则将异常抛给系统，直到app崩溃。如果父协程处理异常，则会先取消掉自己下面的其他子协程的job，然后将异常继续抛给自己的父协程，依次这样去处理异常。
